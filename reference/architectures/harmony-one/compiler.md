# Harmony One: what Logitech's compiler writes

A Harmony One configuration is not only a list of devices and activities. Logitech's software, which
compiled every configuration a Harmony One ever ran, also writes the remote's own screens into it: the menus,
the clock along the top, the help that asks whether the television is off, the settings and the date pickers,
and the welcome tour. It also writes the wiring that connects the firmware to those screens, the lists of
instructions a key press, a timer or a status code runs. Nothing of that comes from the firmware; a Harmony
One draws what its configuration tells it to draw.

This page describes what that compiler writes, measured over nineteen distinct configurations it compiled for
the Harmony One: sixteen English ones of skin 54, two English ones of skin 59, the European One, and one Dutch
one. The rules here are stated as Logitech's and each is checked by rebuilding those compiles byte for byte;
the code that does so is named beside each rule, under `packages/codec/src/families/touch/`. A "compile" is one
configuration Logitech's compiler wrote. "Fixed" is what every configuration holds whatever its setup,
"the setup's" is what a device or an activity brings.

The Harmony 600, 650 and 700 have a page of their own, [the 600 family's compiler page](../harmony-600-650-700/compiler.md),
and the byte level structures named here, base slots, action lists and screen programs, are
[the configuration format](../../config-format/README.md).

## What every configuration holds, in three parts

Every screen byte of a Harmony One configuration is fixed, dynamic or the setup's, with the touch map, base
slot 17, as one unit per hit page[^s405]. **The head of the mode table** is the event map's fallback, the number
of firmware screens, plus its 30 status codes: 40 modes on the One, 3 binding a keypad and 37 not, and 44 or 49
on the Harmony 600, 650 and 700, where this agrees with the reading of their compiles[^s405][^s317]. A
configuration whose events all name one mode carries no status screens, and there the head is the firmware
screens' run alone[^s317]. A page's `0x16` call into its chrome is a transfer in the normal form; each chrome
is called by one mode[^s405].

Over the sixteen English compiles of skin 54, no device or activity name being in all of them, the census
decides the screens structure calls `other`. That rules out a screen naming a device or an activity and not
one a feature every member has brings with it: two generic help screens are in fifteen of the sixteen[^s405].

| category | units on the compile of two devices | bytes |
|---|---|---|
| fixed | 36 pictures, 280 glyphs, 25 hit pages, 9 case programs, and 78 modes: the 40 of the head and 38 others, the welcome tour, screen sensitivity, the clock's pickers, Options, the Remote Assistant at start and seven blank screens | 795905 |
| dynamic | base slot 11 entries 0 to 3, the clock's header programs, and the 16 pictures only they draw | 12203 |
| setup | device modes and lists, help about a device, the activity menu, 6 pictures, 133 glyphs and every font set header, 4 hit pages, 16 case programs, the tables | 285828 |

Fixed is 795792 to 795925 bytes on each of the sixteen, every fixed mode re-encoded per compile and none byte
identical once relocated; only the 38 other modes change size, the rest of fixed being 785417 bytes on
each[^s405]. **Fixed is per skin, per language and per compile**: the two compiles of skin 59 differ in 10
and 4 of the 78 fixed modes (the clock's pickers on both, Options and the absent Remote Assistant on one of
them), and the Dutch compile in 69 of the 78, every one that draws text. Nothing in a configuration states its
language[^s405].

**A screen's page record** is seven bytes on the One, the hit page first, then the list and program
addresses, and a page program calls its chrome with opcode `0x16`, so the mode's own program is drawn first;
`recordReading` in `packages/codec/src/screenrecords.ts` follows that call and spans the chrome as a piece of
its own, and all 40 head screens of all nineteen compiles read and put back come back byte for byte with
nothing generated[^s405][^t-screenrecords-one].

## The firmware's own wiring

The lists, entries and timers that connect the firmware to a configuration are one catalogue on all nineteen
compiles, the same but for three settings, two kinds of timer and their numbering[^s410]. Built by
`buildTouchWiring` in `wiring.ts` from a description `describeTouchWiring` reads, byte for byte on the
nineteen, with every generated byte overwritten in the input first[^s410]. The engine, an instruction's, a
list's and an entry's encoding and the swap into a layout, is `packages/codec/src/wiringparts.ts`, shared with
[the Harmony 600, 650 and 700's wiring](../harmony-600-650-700/compiler.md); `Family.wiring.check` is how shared
code asks for either.

| structure | generated | the description's |
|---|---|---|
| base slot 2, base slot 15 | whole[^s407] | nothing |
| base slot 4 | code `k` to mode `10 + k`, `k` 0 to 29, fallback 10, the ten firmware screens | nothing |
| base slot 8's leading list | `call start` | the start list's index |
| base slot 12 | every record's kind | the rest of each record: the table's order is read off a record's duration and opcode, the screen light pair's durations are settings, and a device's timer is carried whole |
| base slot 9 entries 0 to 6 and the leftover entry | tags, flags, form, stored order, every opcode | what the bindings name; the leftover entry's index |
| base slot 10's front | 168 lists, entries 1 to 4's own in stored order, indices from the first | where the front starts, three past the start list on 19 of 19 |
| the other lists the wiring reaches | every instruction | their indices and the modes, variables, value maps and screen programs they name |
| the 14 lists reached only through the transitions of `readyVar`, `relightVar` and `settleVar`[^s418] | every instruction | their indices: the four the transitions call off the variables' base slot 13 records, the ten below off their parents' calls |
| settings | | the Remote Assistant at start, the ladder's `07 FFFB`, the screen light's two durations |

**The settings**: the Remote Assistant on 18 of 19, the leftover entry wide with it and narrow without, and
without it the ladder is its last rung; `07 FFFB`, the firmware's cancel of all four running timers[^s73],
opening the ladder on 2 of the 18, and refused without the assistant; the screen light pair 10 and 20 seconds
on all 19[^s410].

**Base slot 9's fixed entries**[^s410]: entry 0 binds events `0x1A` to `0x1D` to the events list; entry 1 binds
fourteen tags, ten events and the presses of scans 34, 37, 46 and 47, `0x23`, `0xAF`, `0x26`, `0xAE`, `0x27`,
`0x25` (`00 0000`), `0xA2`, `0xA5` (select the leftover entry), `0x0F`, `0x2D` (`07 FFFA`), `0x10`, `0x19`
(`07 FFF6`), `0x1F` and `0x1E`; entries 2 and 3 bind the presses of scans 1 to 40, 43 to 53 and 55 and tag
`0x30` each to a list of its own, entry 2's `[07 FFFB, call ready, 3F C11C]` and entry 3's
`[07 FFFB, call menu, call lights]`, entry 3 adding `0x17` and `0x26` to the menu list and `0x1F` to `07 FFFB`;
entry 4 binds the presses to `[call lights, call keyLights]` each, `0x30` to the lights and `0x17` to a list of
its own; entry 5 binds `0x1E` to `07 FFFB`; entry 6 binds `0x18` and `0x19` to the events list. The leftover
entry binds `0x01`, `0x05` and the presses of scans 34, 38 and 55, `0xA2` (the assistant's variable to 1, with
flag 1, absent without the assistant), `0xA6` (a value map) and `0xB7`. Entries 0, 3, 4, 5 and 6 are wide,
entries 1 and 2 narrow. Stored in `tagSlotOrder` with the ties `0xAF` before `0x26`, `0xAE` before `0x27`,
`0x0F` before `0x2D` in entry 1; `0x17` before `0x9E`, `0x1F` before `0x96`, `0x26` before `0xAF` in entry 3;
`0x17` before `0x9E` in entry 4; `0xA6` before `0xB7` in the leftover entry.

**The variables and value maps the wiring names**: eighteen variables after the firmware's, each with the same
range and transitions on all nineteen, and of the sixteen value map roles the wiring's five are `readyMap` the
menu record, `menuMap` the working route, `idleA6Map` help, `idleEnterMap` idle and `idleMap` the all off, on
19 of 19[^s430]. The catalogue of sixteen value maps is [the program table below](#the-screen-program-table-and-the-value-maps).

### The timers

Every one is kind 1[^s410]:

```
screen light, its partner   the setting's seconds, 10 and 20   call a list switching the lights off
tick                        2 s     call
lights out                  1 s     call
two of 5 s                  5 s     call, one of them started by entry 1's 0x26 list
enter                       5 s     7E a screen of the configuration's
six of 1 s                  1 s     7E a screen each, the fifth the ready list's
three second                3 s     call [07 FFFB, call lights, enter a screen], on 2 of 19, started by the screen the power off value map enters
redraw k                    4 s     call [73 clock, 73 charging gauge, 1F EB00|k], 13 to 20 per compile, one per class of screen
a device's                  carried whole, on 12 of 19
```

The thirteen are on 19 of 19 once each, in **three orders** over the 19, five with the three second timer's
place[^s410]. A record is generated in its kind byte alone: the reader names each timer by its duration and
opcode, and the two pairs those cannot tell apart by the list starting each, so a screen light of 1 to 5
seconds would share a length with another timer and is not read[^s410]. The three second timer's screen is the
attempt screen of the power off help on the one compile with nothing to switch off, and there it enters
"Nothing to do"[^s430].

**The redraw timers are one per class of screen**[^s430]. Every redraw timer is started by the enter handler
(tag 6) of at least one mode, bound directly or in the list it calls, and no mode starts two: 3195 modes over the
19 start one, none starts two and no redraw timer is started by none. P and Q are the clock header's clock and
then its charging gauge on 19 of 19. The screens starting one timer, named by the screen sets' finders on the
sixteen English compiles of skin 54:

| class | its screens |
|---|---|
| low battery | firmware screen `lowBattery` |
| progress and status | the five firmware progress screens, the 29 status screens, "LCD Module Failed" |
| charging problem | firmware screen `chargingProblem` |
| activity menu | the activity menu |
| help after the attempt | the power off help's screens after the attempt ("If not" and the questions, or "Nothing to do"), and screens the activities bring |
| device lists | every device list |
| sensitivity confirmations | the five, four of the Remote Assistant's screens, and four screens per activity |
| Year and Options | the Year picker and Options |
| Screen Sensitivity | Screen Sensitivity |
| clock pickers | Month, the three Day pickers, Hour, Minute, Time of Day |
| help attempt | the attempt screen, and one screen per activity |
| device pages | every device's mode, where the finder names them (15 of the 16) |
| Hide Question | the Remote Assistant's "Hide" question, and one screen per activity |

So a configuration with no activity holds thirteen, 4 of 4, and the activities' start up, working and other
screens add classes of their own, 0 to 7 over the sixteen. The welcome tour's eleven screens start none. The
classes' order in the table is the compile of two devices' and not a rule: the sixteen hold 14 orders[^s430].

### The key lights and the screen light

A three instruction list `[3F C0a2, 3F C0b2, write 1]` sets channels `a` and `b` of the device at `0x60` on,
the same with `C0a0`, `C0b0` and a write of 0 off. Channels 3 and 1 or 2 and 0 are the keys beside the screen.
A screen's tag `0x07` list calls the pair's off list, and its tag `0x06` list calls the on list, one to four
instructions in, wherever both page keys do something: 337 of 337 screens of several pages and 95 of 95 one
page screens binding both page keys; none of the 408 others[^s400]. `withPageKeyLights`. The screen light is
the 10 second timer of the one pair of timers queueing two lists of the same content, 10 and 20 seconds, in all
nineteen compiles; its index varies, so it is found by that shape[^s400].

## The screens every configuration holds

### The ten firmware screens

`firmwarescreens.ts` describes the two fonts, the hit pages, thirteen pictures and the configuration's numbers
(lists outside the screens, timers, base slot 11 programs) and generates the rest[^s409]. On the seventeen it
rebuilds, base slot 10's first 178 lists are these screens', numbered in stored key order with each chrome's
queued list after its keys. Lines are centred, `floor((176 - width) / 2)`; "OK" at 124, 201. Three shared
buckets are stored in an order measured the same on all nineteen; the insertion order that produces it,
`keyListOrderInserted`, is inferred. Rebuilt byte for byte on the sixteen English compiles of skin 54 and the
European factory file[^s409]. The 18 lists the screens reach that the wiring does not build are built too, at
the indices the description reads[^s418]. Which of them the firmware itself enters is
[the platform's firmware page](firmware.md#which-screen-the-34-firmware-draws).

### Twenty three more fixed screens

(28, 30 and 31 days), Hour, Minute and Time of Day pickers, and seven blank screens[^s411].
`fixedscreens.ts` finds each by its look, describes which mode it is, its hit pages, pictures, fonts by role,
the build year and the configuration's numbers (list indices, modes, timers, base slot 11 programs, value maps,
state variables), and generates the rest; the 531 lists the screens name directly are built at the described
indices, and so are the 154 below them the wiring does not build[^s411][^s418]. The other 53 below them are the
wiring's.

configuration[^s403]. 98 lists built per compile, 66 without the assistant, and the 17 below them the wiring
does not build (13 on five compiles, 3 on the one without the assistant), with the one setting that decides
their shape[^s418].

| a state write bound in a key map | its opcode, `0x80 + variable`, is the description's; the value is the template's |

| which "Ensure all your devices are off" is which | the one the wiring's ladder enters, `assistantDevicesOff`, whose OK enters the question; the other, whose OK runs a list |

**The Remote Assistant at start** is one unnamed state variable, running 0 to 3, tested by a ladder of lists
loading 1, 2 and 3 into the byte register (`1F FB0k`, then a test `71`), the first two rungs entering the
welcome and the "devices off" screens (English on 17, Dutch on the Dutch compile), the third going on with the

the activities' assistant screens write 2 and 3 too. It starts at 0 in Logitech's compiles; starting it at 3
starts the remote on its ordinary screen[^s403][^s403b], `withoutStartupAssistant`. The "Welcome!" screen
follows the "devices off" screen's OK; its own variable, 0 to 1, is written 0 silently by a list of every
compile, so its starting value is not what decides it[^s403].

**Leaving the tour and the assistant out**[^s421]. The sixteen modes, base slot 6's count, every `0x7E` and
event map value naming a mode above them renumbered; three paths reach them outside themselves on a compile, and
each has to stop: the start's ladder and the leftover entry's events 1 and 5 that run it (the wiring then takes
the one compile without the assistant's start, the ladder's last rung alone and the leftover entry narrow),

48, the sounds' value map on 49 and Screen Sensitivity on 50, the key's value map at 51, its own key map taking
scans 46 and 47 to nothing[^s275] and drawing no page count or number, on the hit page of three rows, a form no
compile holds), and the OK of "Devices Off Again". Base slot 10 loses every list reached before and by nothing
after, and every list nothing reached before that names one of those, three on five of the sixteen English
compiles of skin 54; base slot 17 loses the pages only the sixteen named; the eleven pictures only they drew go.
**A text drawn by reference may point into any screen**, and on 14 of those sixteen a page that stays draws
into one of the sixteen, so every text is first drawn as if the sixteen and Options came last and, after the
cut, the text form rule is applied again[^s406]. 245246 to 245593 bytes shorter on the sixteen, and every
builder of the touch family rebuilds the result byte for byte. What stays reached by nothing: the assistant's
value map, its two case programs and their lists, and the assistant's and the welcome's state variables. A
configuration so made started on a unit on its ordinary screen, and Options showed the one page of three
rows[^s421b]; `withoutTourAndAssistant` in `withouttour.ts`.

### The clock header

bytes of lists; 3516 bytes of programs on the sixteen, 3537 on the European two and 3509 on the Dutch one;
rebuilt byte for byte on the sixteen and both European compiles, the Dutch one refused.

## The click before a screen send

**Logitech's compiler clicks before every screen send on the Harmony One.** Every screen binding that sends runs
`0x75 0x0FCA`, then its calls, then its `0x7D`, and no key binding that sends runs it, on four of Logitech's
compiles[^s337]; a configuration that omits it still sends, so it is a convention and not the remote's
demand[^s337b]. What the tone costs a send is [the action language](../../config-format/actions.md#0x75-sounds-a-tone).
A screen binding's send is also more often a **one block copy**, whose once block opens with its
device's delay between devices, 500 or 1000 ms on the One, where a two block record opens with 50 ms: 148 of one
compile's 241 screen sends against 23 of its 377 key sends[^s337]. **A device page's row, a `0x7F` binding, runs
a list that opens with the click**, on 3545 of 3545 rows over the nineteen: `{0x75 0x0FCA, 0x7F list}` on 3495,
the click and a `0x72` on 50. The touch family's device page wraps every row whose list does not already open
with a click that way, and an activity screen's pad, which clicks itself, calls the command under the device
page's click, so no binding reaches two clicks, as none in Logitech's compiles does. The Harmony 600, 650 and 700
compiles' device page rows open with a call instead[^s404].

## Pictures

**The whole screen background is all black and stored more than once**: raw, 176 by 220, every pixel `0x0000`,
77445 bytes, three times on four of the sixteen English compiles of skin 54 and four times on the other twelve,
each copy byte identical, and drawn by 66 to 314 instructions a compile[^s422]. Six of the seven blank screens a
timer enters draw three photographs of the same size instead, two screens each, and the seventh draws the
charging screen's picture[^s422]. Logitech stores other images several times too: the full gauge at three of the
clock header's addresses and a settings button once per place it is drawn[^s414][^s422]. **A picture nothing
names is not a piece of its own** to `takeApart`: its bytes are carried on the end of the piece before it, so
taking one out is a cut by the extent its header states[^s422].

**Which fixed pictures leave pixels undrawn**, the same on every stored copy of all nineteen compiles: of the 29
images behind the 23 drawings `pictures.ts` names, the ten battery gauge pictures, 20 by 11, and the charging
problem's cross, 87 by 62, and no other. Every gauge picture leaves its row 0 and column 0 undrawn, 30 pixels,
but the battery gauge's level 0, Logitech's grey question mark, which is drawn at every pixel; eight leave three
or four pixels more at the picture's corners, the charging animation's third frame a fifth inside its body;
level 3 leaves 69, its bottom row and most of the right end of its body and tip among them. The cross leaves
4028 of its 5394 undrawn, everything outside its circle's silhouette, a roughly round blob of 1366 drawn
pixels[^s428]. What that shows on a screen is [the One's display page](../../remotes/harmony-one/display.md#how-the-screen-is-drawn).

**A filled rectangle has three uses on Logitech's compiles**: over the sixteen English compiles of skin 54
Logitech uses [opcode 1](../../config-format/screens.md#filling-a-rectangle) for the welcome tour's black
background, 11 a compile, for a black fill before a full screen picture, 18 in all, and for the four lines two
pixels wide that frame a picker's button, 9 frames a compile, each closing exactly round a button picture drawn
there, 144 of 144[^s425b].

The Harmony One gets this project's own pictures in place of Logitech's[^d24]; how they are drawn is described
in `pictures.ts`.

**Placement**: the pictures and glyph sets are placed by the same rule as on the Harmony 600 family, with nothing
of the One's own, [the layout reference](../../config-format/layout.md)[^s426].

## State tables and a device's inputs

**A device's inputs** are the Harmony 600 family's on the Harmony One, but for the send, which is two
instructions there, [the 600 family's compiler page](../harmony-600-650-700/compiler.md)[^s393]. The catalogue's
`power.onReset` lists come after the power variable's wait in 3 of the 19 compiles, in the same shape[^s393].

**The state tables are built by the same builder as the 600 family's**, with what differs held as each family's
`StateTableFacts`, the Harmony One's `TOUCH_STATE_TABLES` in `statetables.ts`. All 19 distinct compiles rebuild
byte for byte from a description, and from a blinded one, the clock's seven records, the firmware's eleven and
the first two byte variable among them[^s407]. What is the Harmony One's own:

| what | value on the Harmony One |
|---|---|
| records 7 to 17, `first / max` | `0/2, 0/3, 5/7, 0/7, 0/32, 0/1, 1/1, 2/4, 0/3, 0/1, 0/3`, no transitions[^s407] |
| a variable's width | one byte for a maximum up to 121; no two byte variable but index `narrow` on any of the 19, so a maximum past 121 is refused[^s407] |
| a value map's case count | one byte, `VALUE_MAP_COUNT_WIDTH`[^s407] |
| index `narrow`, the first two byte variable | the clock pickers' variable: the one the seven pickers' tag `0x29` handlers read and write and the `grid` and `column` value maps are looked up on, on all sixteen English compiles of skin 54[^s432] |
| the assistant variable USB Connected's leaving list tests | 0 to 3, `first` 0, unnamed, on the sixteen, whose wiring holds the Remote Assistant's ladder, and on two more compiles read by hand[^s432] |
| Time of Day's variable | 0 to 1, `first` 0, unnamed, written 0 by AM and 1 by PM, on the sixteen[^s432] |
| the minute's second transition | `{-2 to -2, 0x7F list}` after its increment of the hour, on all 19: since both ends are the sentinel it fires on every write of the minute that is not silent, and the list it calls is the clock's screen side, calling two short lists, its index the configuration's (`minuteList`); on all 19 that list sits straight before the hour's[^s407] |

The clock's other transitions, the hour's list `[0x1F 0xF203, 0x1F 0xF204]`, index `narrow`'s `0/65277`, the
value map lead byte and the name tree's roots and order are the 600 family's on all 19[^s407]. What the records
mean is [the One's memory page](memory.md).

## What no compile shows: a Harmony One with no device

Every one of the nineteen compiles holds at least one device, so a configuration with none, base slot 5 with no
infrared group and device lists of no rows, is shown by none of them[^s434]. The fewest modes and lists any
compile holds are 84 and 1955, the fewest base slot 11 entries 29, and the fewest timers 26[^s434][^s430]. What
the compiles do show near zero: an activity menu of no row and the thirteen redraw classes of a configuration with
no activity, on the four compiles with none[^s429][^s430]; and an all off with nothing to switch off, with its
help chain of the attempt screen and "Nothing to do", on one compile[^s415][^s430].

**How wide each table's count is**, on 19 of 19 compiles, read as each table's length less three bytes per entry
it names: one byte for base slots 5, 9, 12, 15, 16 and 17, two for 10 and 11, and three for 6. Reading the same
tables at four bytes an entry disagrees with the widths on 19 of 19, which is the control. Raw slot 18 is two zero
bytes with nothing parked in front on all nineteen[^s431]. `TOUCH_COUNT_WIDTHS` holds the widths.

**Within a mode, Logitech's order** is the own key map, the chrome, then per page its program, its switch's pieces
and its page record, then the entry, on all 102 device lists of the nineteen compiles[^s435].

**What a builder adding the first device needs**, read off Logitech's compiles because a configuration with no
device does not hold it[^s435]:
