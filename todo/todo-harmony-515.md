# The Harmony 515: what the FHSDK can do for it

Every requirement possible on the Harmony 515, by subject, ticked where a test proves it. The list is generated by
`make requirements-write` from the requirements data and the proofs in the tests, so a box changes with a test and
never by hand; an impossible requirement is left out, and one marked "find out first" is not known to be possible.
An open one says in brackets whose work is missing: the FHSDK, done once for every remote; its family; the remote
itself; or only a run on a unit.
What each requirement means is [the requirements](../docs/remote-requirements.md), and what a box rests on
[the evidence](../docs/remote-requirements-evidence.md).

## The remote's own work

Work for the Harmony 515 that no requirement above names, written by hand and kept when the list is regenerated.

The bench unit may be written, decision 35; each write path opens as its own step, one block back unchanged before
a real write, as on every unit. Load the `harmony-515` and `harmony-525` skills first.

### 1. Before the first write

- [ ] Check the 525's write rails and addresses against the 515's own memory: the configuration region, the firmware one block below, the log area.
- [ ] Read the processor's internal flash and EEPROM into the lab, as the 525's backup took, through a library script.

### 2. The first writes

- [ ] The 515 a flash block target: one block of its configuration region written back unchanged.
- [ ] A whole configuration written to it, once a writer serves the 525's platform.

### 3. Loose ends

- [ ] Each key's scan code measured on the 515, and whether its matrix is the 525's (R43).
