# The Harmony 525: what the FHSDK can do for it

Every requirement possible on the Harmony 525, by subject, ticked where a test proves it. The list is generated by
`make requirements-write` from the requirements data and the proofs in the tests, so a box changes with a test and
never by hand; an impossible requirement is left out, and one marked "find out first" is not known to be possible.
What each requirement means is [the requirements](../docs/remote-requirements.md), and what a box rests on
[the evidence](../docs/remote-requirements-evidence.md).

## The remote's own work

Work for the Harmony 525 that no requirement above names, written by hand and kept when the list is regenerated.

The open items of the preparation track, `todo/done/todo-prepare-525.md`, which is archived with its ticked items; its rows (D1, F1 and so on) are [plan 012](../docs/plans/012-the-legacy-remotes.md)'s. The 515 shares the platform. Before any item: the legacy remotes handover in the lab and the `harmony-525` skill, the item's brief written into the lab first. **Safe mode is never entered on either model.** Composing an activity for the 525, R21, starts from the rail table item 5.1 closes.

### 1. Recovery and the write path, read in the firmware

- [ ] 1.1 Whether safe mode accepts an erase and a write, and whether the bootloader is a USB flash programmer (D9)
- [ ] 1.2 Whether the remote erases before it programs, and `WRITE_FLASH`'s data path (D3)
- [ ] 1.3 The restart escape and `WRITE_MISC` selector 2 read, to confirm or refute that a write needs neither (D6)
- [ ] 1.4 What the validator at `0x04DF0` checks: cookies, end marker, checksum and its seed (D7, F1)
- [ ] 1.5 The data memory write's handler, the `0x30` address window, and the EEPROM beyond byte 0 and the identity (D11)
- [ ] 1.6 `READ_MISC` selector 1 decoded correctly, and so a USB read of the clock (D12)
- [ ] 1.7 A configuration larger than one 64 KiB block: how it is laid over the region and written, since the 515's and a contributed 525's are (D1)
