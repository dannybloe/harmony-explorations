# The Harmony 785: what the FHSDK can do for it

Every requirement possible on the Harmony 785, by subject, ticked where a test proves it. The list is generated by
`make requirements-write` from the requirements data and the proofs in the tests, so a box changes with a test and
never by hand; an impossible requirement is left out, and one marked "find out first" is not known to be possible.
What each requirement means is [the requirements](../docs/remote-requirements.md), and what a box rests on
[the evidence](../docs/remote-requirements-evidence.md).

## The remote's own work

Work for the Harmony 785 that no requirement above names, written by hand and kept when the list is regenerated.
Both bench units may be written, decision 34; each write path opens as its own step, one block back unchanged before
a real write, as on every unit. Load the `harmony-785` skill first.

### 1. Before the first write

- [ ] Read the write end in the 720's application 4.5: the cache drop, the restart and the staged install status address.
- [ ] Read the bootloaders' refusal of an erase or a write below `0x010000`, in the 720's 4.2 and in the 4.4 build.
- [ ] Draw the 785's face from the unit, each key's scan code read with the key page (R43, R67).

### 2. The first writes

- [ ] The 785 a flash block target: one block of remains written back unchanged on unit A, then on unit B.
- [ ] The 785 among the configuration writer's units: a unit's own configuration written back restamped and taken up.

### 3. Loose ends

- [ ] What a log area entry is, one on unit A and 118 on unit B.
